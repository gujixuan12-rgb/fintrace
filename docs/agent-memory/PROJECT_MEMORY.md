## 官方硬要求（原文，不可自行放宽）

1. 「参赛作品应**至少使用一个大语言模型**作为核心推理引擎，鼓励采用国产模型」——
   纯规则实现按决赛标准**不合规**。
2. 「应以结构化数据、表格或分析报告等形式呈现，**不得仅提交自然语言对话记录**」。
3. 「须在封闭或半封闭数据环境中运行，完整记录文件访问、工具调用、计算过程和结果
   生成情况，确保**数据来源可核验、执行过程可追溯、运行结果可复现**」。
4. 「须同步提交与现场展示版本一致的完整源代码，包括**智能体编排框架、Tool、Prompt、
   Skill、MCP、数据处理和日志记录**等核心模块」。
5. 「涉及估值或投资判断的，应说明主要假设、适用范围和风险因素，并**明确区分事实、
   推论与观点**」——这是措辞约束在官方口径下的对应表述。
6. 选题五的评测重点原文：「**错误识别的准确性和覆盖率、误报控制、来源定位以及修改
   建议的可执行性**」——即要求可量化评测。
7. 选题五的场景定义原文：「依据原始财务材料，对**给定研究报告草稿**中的收入、利润、
   估值倍数、单位、统计口径和引用等内容进行核查，识别错误并提出修改意见」。

## 长期不变量（不要改坏）

1. **数字必须来自程序化复算，模型不负责算术。** 模型负责检索、假设拆解与措辞。
2. **任何结论都要能回溯到「哪个文件、第几页、哪句话」。** 定位不到就诚实输出
   「当前公开信息不足以确认」，绝不编造页码。
3. **不做定性断言。** 系统只输出风险信号与核查建议，措辞受代码级守门人约束
   （`verification/wording_guard.py`）。
4. **评测必须可复现。** 每条 run 都有运行日志编号，同一输入必须产出同一结果。

## 关键设计取舍

| 取舍 | 选择 | 理由 |
|---|---|---|
| 模型 vs 规则 | 规则打主干，模型做拆解与措辞 | 调错时能区分是规则错还是模型错；且算术不能用模型 |
| 包结构 | `src/fintrace/<五子模块>/` | 比队长给的 `src/<五子模块>/` 多一层包名，Python 打包与导入需要 |
| 约束位置 | 代码层，非提示词 | 提示词约束不可验证；代码层可测试、可回归 |
| mock 公司 | 虚构公司 | 避免把编造的数字安到真实上市公司头上 |
| 案例材料的错误类型 | 按**披露一致性**而非**财务异常**建模 | 6 组真实案例全是披露差错，不是舞弊（见 `docs/CASE_ANALYSIS.md`） |
