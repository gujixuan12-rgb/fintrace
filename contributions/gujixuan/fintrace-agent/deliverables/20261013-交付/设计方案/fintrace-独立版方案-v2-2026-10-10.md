### 0.2 我在三条之外补的三个工程保障（不是反对，是配套）

1. **可复现性改用「决策日志重放」而不是固定顺序。** 自主规划确实让执行路径变成变量，
   但解决办法不是把路径写死，而是把每次决策记全：`decisions.jsonl` 里落
   `(state_digest, prompt_version, model, action, args_digest)`。同一个 run 重放得到同一动作序列；
   评测基线仍跑 fixed 模式，于是现有 294 项 / 26-26 / 19-19 的口径一个都不动。
2. **二手线索不得单独支撑「矛盾」结论。** 网页来源拿不到页码级出处，
   所以它进的是线索层，只有解析回官方原文才能升为证据（第 5 节的 L1~L4）。
   这条不加，原件回查那个 19/19 就会被稀释。
3. **验收指标体系与 fixed 基线分开跑、分开报。** 你的第 9 条我完全接受，
   但新指标在 2 个自造样本上只能证明「口径能测」，不能对外称泛化能力——
   这与项目现有纪律一致（`run_draft_eval.py` 自己会打印「不得外推」）。

## 1. 总纲：谁决定、谁执行、谁能说不

| 角色 | 是谁 | 职责（你的第 6 条） | 权限边界 |
|---|---|---|---|
| Agent | DeepSeek | 规划调查路径、语义抽取、候选关系发现、定性推理、必要时独立审查、**格式不认识时当场编写受限抽取器** | **只能选动作**。不能算数、不能改判定、不能发布；自写代码必须过沙箱与同一道 W 门 |
| Python 执行与约束 | 确定性代码 | 数据处理、精确计算、口径约束、证据验证、执行边界、自写工具的静态审查与沙箱 | 能执行、能拒绝、能停机 |
| Task State | 落盘 JSON | 目标、进度、待解决问题、证据索引（**只存索引，不存正文**） | — |
| 证据库（原文层） | 落盘 + 原始文件 | Document 与 Evidence Span，只追加、不删除、不覆盖 | — |
| 公司事实库（实例层） | SQLite | 已核验的 Assertion 与 Relation | 未过 W 的不进 |
| 领域知识库（规则层） | SQLite | 概念、公式、财务关系及适用条件 | 不能覆盖代码判定；变更需人审 |
| 最终核验门 V | 确定性检查 + 按需审查模型 | 逐条 Finding 的证据充分性、关系适用性、发布审核 | 决定哪条能发 |

三条不可让渡：**终止权不在模型手里**（模型只能「请求结束」）；**判定权不在模型手里**
（数值、单位、口径、标签来自代码）；**发布权不在模型手里**（V 门逐条裁决）。

## 2. 数据模型：Document → Evidence Span → Assertion → Relation

这是你第 2 条，也是 v2 与团队仓库现状差距最大的一处。逐层给契约。

### 2.1 Document（材料层）

```jsonc
{ "doc_id": "D-0001", "source_id": "...", "file_name": "2023年年度报告.pdf",
  "source_type": "original_annual_report",        // 沿用 models.SOURCE_TYPES 八类
  "publication_date": "2024-03-29", "page_count": 237,
  "acquisition": "local | cninfo | web",           // v2 新增：怎么来的
  "content_path": "data/raw/002232/...pdf",        // 原文必须留档，不删除
  "content_hash": "sha256:...",                    // 指纹口径沿用现有实现
  "available_before_cutoff": true }
```

现状：`models.SourceDocument` 已有，字段基本够用，缺 `acquisition` 与 `content_hash`（后者在 `site.py` 里算出但没落到这个对象上）。

### 2.2 Evidence Span（原文层，只追加）

一段**可精确定位**的原文：表格单元格、表格行、段落、标题、附注。

```jsonc
{ "span_id": "S-000123", "doc_id": "D-0001", "page": 51,
  "char_range": [1204, 1231], "quoted_text": "408,548.46",
  "decimals_as_disclosed": 2,                             // 披露几位小数，原样记录，不许截断
  "span_kind": "table_cell | table_row | paragraph | title | note",
  "bound_context": { "row_label": "现金分红金额（含税）", "col_label": "本期",
                     "unit": "元", "period": "2023A" },   // 行列绑定结果
  "rect": [x0, y0, x1, y1] }                              // 红框坐标，报告用
```

现状：`draft_review.py` 里 `PageRec`(274) / `Token`(290) / `_ev()`(973) 已经在算这些东西
（`_ev` 已经带 `row_label`、`raw`、`page`），但**没有 span 这个概念**——
它是「临时令牌」，用完即弃，跨轮不累积，也没有 `char_range`。
v2 要做的就是把这个中间态固化成对象：**这就是你第 2 条里最实际的一步。**

### 2.3 Assertion（断言层，覆盖五类内容）

从 Span 提炼出的、可以独立读懂的陈述。**必须能覆盖财务数值以外的东西。**

```jsonc
{ "assertion_id": "A-0007", "kind": "financial_value | operating_event | fact_statement | forecast | opinion",
  "subject": "启明信息", "period": "2023A", "metric": "现金分红金额",
  "value": "408548.46", "unit": "元", "caliber": "合并 | 母公司 | 扣非 | 不适用",
  "direction": null,                     // 上升/下降/持平，事件类与比率类用
  "raw_text": "408,548.46",              // 原文原样，一位不改
  "decimals_as_disclosed": 2,            // 披露了几位小数就存几位
  "text": "2023 年度现金分红金额 408,548.46 元",
  "source_spans": ["S-000123"],          // 一手证据；可为空（此时不得判矛盾）
  "extracted_by": { "how": "rule | llm", "model": "deepseek-chat", "prompt_version": "p3" },
  "origin": "material | draft | engine", // 材料披露 / 草稿主张 / Python 复算
  "evidence_status": "candidate | attested | rejected",   // 轴一：证据真实性（W 门）
  "semantic_status": "unbound | bound | conflicted",      // 轴二：语义绑定正确性（独立检查）
  "gate_trace": { "w_checks": ["W1","W2","W4","W6"],
                  "binding_checks": ["B1","B2","B3"], "at": "..." } }
```

要点四条：
- **`origin` 区分三个来源**（沿用团队仓库 `explanation_guard` 已经验证有效的三分法：
  `material` 唯一能当出处，`draft` 是被核对象，`engine` 永不作出处）；
- **两轴必须同时满足才算事实**（你的第 1 条）：`evidence_status=attested`（原文确实存在、
  可定位、时间合法）**且** `semantic_status=bound`（指标解析到标准概念、事件状态与时态正确、
  统计范围与披露一致）。只过了 W 而语义没绑定的，**不得支撑 `CONTRADICTED`**，
  只能停在候选或标 `conflicted`；
- **模型抽取的默认是 `candidate` + `unbound`**，两轴都要各自过门；
- 五类内容各有必填项：`financial_value` 必须 `value+unit+period`；
  `operating_event` 必须 `text+period`；`forecast` / `opinion` **不得进入矛盾判定**，单列；
  数值一律带 `raw_text` 与 `decimals_as_disclosed`，提取阶段原样保存（6.4）。

### 2.4 Relation（关系层，必须带适用条件）

```jsonc
{ "relation_id": "R-0003", "predicate": "contradicts | equals | derives_from | supported_by | changes_by | belongs_to",
  "subject_ref": "A-0007", "object_ref": "A-0012",
  "applicability": {
    "period":        { "claim": "2025A", "evidence": "2025A", "match": "verified" },
    "caliber":       { "claim": "合并", "evidence": "合并", "match": "verified" },
    "unit":          { "claim": "元", "evidence": "元", "rate": "1:1", "match": "verified" },
    "scheme_id":     { "claim": "2025年度利润分配预案", "evidence": "S-000071", "match": "verified" },
    "scheme_status": { "claim": "预案（待股东会审议）", "evidence": "S-000071", "match": "verified" },
    "scope":         { "claim": "单一方案", "evidence": "单一方案", "match": "verified" },
    "base":          { "claim": "2429119230", "evidence": "2429119230",
                       "base_date": "2025-12-31", "match": "verified" },
    "effective":     { "board": "2026-04-23", "agm": null, "implemented": null, "match": "verified" },
    "rule_id": "cash_dividend_total", "rule_version": 3 },
  "status": "candidate | verified | rejected",
  "verified_by": { "checks": ["APP-1","APP-2","APP-3","APP-4"], "at": "..." } }
```

**两条规则**（你的第 2 条）：

1. 适用条件的每个字段都是 **(主张值, 证据值或出处, 匹配结论)** 三元组，`match` 一栏
   **由程序依据证据填**；模型可以提出「这两条该比」，但模型填的 `true` 一律忽略。
2. 任一项 `match=failed` 时**不得判矛盾**，只能降级为 `INSUFFICIENT`，并写明是哪一项不成立。

**为什么三个布尔挡不住 —— 生益科技 2025 年报（600183）里同时有四个「分红方案口径」：**

| 方案 | 每 10 股派息 | 基数（股） | 状态 | 金额（元） |
|---|---|---|---|---|
| 2024 年度 | 6 元 | 2,429,360,530（实施登记日） | 已实施（2025-05） | 1,457,616,318.00 |
| 2025 年半年度 | 4 元 | 2,429,262,930 | 已实施（2025-09） | 971,705,172.00 |
| 2025 年度预案 | 8 元 | 2,429,119,230（2025-12-31 测算） | 预案，待股东会 | 1,943,295,384.00 |
| 第 50 页「本报告期预案表」 | **12.00 元** | 2,429,119,230 | 半年度（已实施）+ 年度（预案）的**合计** | 2,915,000,556.00 |

四个方案、三个基数、三种状态。期间/口径/单位全对的情况下，只要 `scheme_id` 或 `scope` 绑错
（拿「8 元预案」去核「12 元合计」，或拿 2024 年度的 6 元去核 2025 年的说法），
就会产出一条看起来证据充分的误报。这正是你点名的那个场景。

现状：判定链里已经有期间绑定、口径核对、单位换算（`_out_of_scope`、`_claim_caliber`、
`to_base`、`_deducted_row_token`），但它们是**过程内变量，跑完就没了**，也没有方案维度的绑定。
独立版要把它们固化成可审计的 Relation，并把方案维度补上。

### 2.6 顺带修一处既有口径冲突（本轮读代码发现）

## 4. Agent Loop：自主路径 + 硬边界 + 两道门

### 4.1 什么固定、什么不固定（你的第 1 条落成清单）

| 类别 | 内容 | 谁定 |

### 4.4 Context Builder（你的第 4 条）

Task State 只记四样，**不存正文**：任务目标、进度、待解决问题、证据索引（`span_id` / `assertion_id` 列表）。

每轮上下文这样组装（不是回放历史，也不是只发压缩摘要）：

| 块 | 内容 | 来源 |
|---|---|---|
| 1 固定头 | 任务目标一行 + 硬边界剩余额度 + 输出契约（严格 JSON） | state.bounds（Python 算好的数字） |
| 2 待解问题 | `open_questions` 列表（这是驱动检索的键） | state |
| 3 按需取回的原文 | 由 2 里的问题去证据库取**相关 Span 原文片段**（不是摘要）；必要时按页范围/关键词召回 | 证据库 |
| 4 按需查询的规则 | 命中指标的公式与适用条件（只在这轮确实要用时注入） | 领域知识库 |
| 5 已核验事实 | 相关 `(subject, period, metric)` 的 verified Assertion 摘要 | 公司事实库 |
| 6 上一轮收据 | 工具 / 成没成 / 新增证据条数 / 一行摘要 | state.steps 尾条 |

明确不送：年报正文全文、全部历史工具输出、已 close 主张的证据细节、其他案件的任何东西。
**同一 `artifact_fingerprint` + 同样 state → 同样上下文**，这是可复现性的落点；
token 量从「每次全量」压到几百量级。

**时间基准（你的第 3 条）**：组装上下文时按 `as_of` 过滤，而不是只过滤证据本身。

| 模式 | Agent 能接触到什么 | 输出口径 |
|---|---|---|
| `historical_replay`（历史回放） | 只有 `first_published_at ≤ cutoff` 的材料**与线索**；检索请求也带 cutoff | 结论按「当时可得信息」出，报告写明截止日 |
| `post_hoc_review`（事后验证） | 全部材料 | 每条结论标 `post_hoc`，不得混进事前口径的结论里 |

规则：**晚于 cutoff 的线索一律不进决策上下文**。理由是你点到的那条——线索即使不作证据，
也能改变 Agent 的注意力（先去查什么、放弃什么），这本身就是未来信息泄漏。
每轮把 `as_of` 与「本轮上下文里最早/最晚的线索首曝时间」写进 `decisions.jsonl` 供事后审计。

为了让 Agent 能主动取回原文，工具集里有两个检索动作（不是只给模型看摘要）：
`t_lookup`（查事实库/知识库）与 `t_recall`（按关键词或页范围召回 Span 原文）。

### 5.4 运行时工具自举（LLM 当场写 tool）

**按你第 5 条，这项能力从里程碑里移出去，但保留一条不用执行模型的过渡路径。**

**为什么移出。** Python 层的导入白名单与禁用调用表**不等于安全沙箱**。真要执行模型生成的代码，
需要操作系统级隔离：独立低权限账户 + 目录 ACL + 资源限制（Job Object 或容器配额）
+ 无网络 + 只读挂载。这套没做出来之前执行模型生成的代码，等于把时间硬门、出处要求
与数值红线一起交出去。所以它列为 **M5 之后的探索项，默认关闭**，
不作为任何里程碑的验收条件。

**过渡路径：声明式抽取规格（`t_spec_extract`）。** 遇到没有提取器的格式，Agent 不写代码，
写一份**规格**，由**既有已审的通用抽取引擎**解释执行：

```jsonc
{ "spec_id": "SP-002", "target": "研报草稿.docx",
  "fields": [
    { "name": "claim_text", "locate": { "kind": "paragraph", "contains": ["预计", "营业收入"] },
      "extract": { "kind": "text" } },
    { "name": "value",
      "locate": { "kind": "regex_in_paragraph", "pattern": "收入([0-9,.]+)(亿元|万元)" },
      "extract": { "kind": "group", "index": 1 } } ],
  "unit_hint": "亿元", "period_hint": "2026E" }
```

好处是三条：不执行模型写的代码；可静态校验（字段名与定位算子都在白名单里）；
可重放（规格落档带 hash）。它覆盖绝大多数「格式不认识」的情况；
真到了规格也表达不了的程度，再谈隔离执行。

**以下六道流程与两条硬规则保留为接口设计（不实现）：**

**它只能是什么。** 只能是一个「抽取器插件」，契约固定为
`extract(document_path, page_range) -> list[Span]`，输出与 `t_parse` 的收据 schema 完全一致。
不能是任意脚本，不能改判定，不能碰网络。**生效前置条件：OS 级隔离成型。**

**流程（六道）**

| 步 | 做什么 | 谁 |
|---|---|---|
| 1 | Agent 发现格式不认识或抽不出 Span，提出 `t_author_tool(goal=…)` | Agent |
| 2 | 生成代码：单文件、纯标准库、无网络、无第三方依赖、无 `subprocess` | Agent |
| 3 | 静态审查：导入白名单 + 禁用调用表（文件只读材料目录、禁 `socket` / `requests` / `eval` / `exec`） | Python |
| 4 | 沙箱试跑：材料只读、无网络、超时默认 20 秒、内存与输出条数上限；**跑通才准登记** | Python |
| 5 | 产出 Span → **过同一道 W 门**（来源、时间硬门、行列绑定、值形态） | Python |
| 6 | 代码落档 `runs/<run_id>/tools/<name>.py` + sha256 + 生成理由，进人审队列 | Python |

**两条硬规则**

1. **未经人审的抽取器只能出 `manual_review`。** 它抽出的值仍需 Python 复算（数值红线不受影响），
   但「它作为抽取来源的资格」必须由人确认——否则「当场写一个抽取器」就成了
   绕过时间门与出处要求的后门。
2. **同一份材料 + 同一次 run 可重放。** 代码带 hash 落档，重放同一 run 用同一份代码，
   不重新生成；否则同输入不同输出，第 9 节的指标全部作废。

**人审通过之后**：抽取器进 `plugins/extractors/`，下一份同类材料直接路由到它，
并同步进 5.3 的路由表。

**5.3 路由表的最后一档随之改写**：格式不认识时，先试 `t_spec_extract`（声明式规格），
规格表达不了才记一条「需要隔离执行」的待办，不落地成自动执行。

## 6. 知识系统：两组库、四个接口

### 6.1 领域知识库（规则层）

```
resolve_metric(name_or_alias)        -> metric_id + 定义域 + 基准单位
formula(metric_id, caliber)          -> 表达式 + 输入项 + 舍入规则 + 适用条件
relation_rule(rule_id)               -> 关系定义 + 适用条件（期间/口径/单位）
context_check(entity, period, unit)  -> 三元组是否与主张一致
```

对齐 XBRL 的收益是实打实的：element（是什么）与 context（哪个期间、哪个维度、什么单位）分开表达，
正好对上我们踩过的三个坑（口径、期间、单位）。所以 `metric_id` 采用 taxonomy element 名，
`caliber` 落成 context 维度，让「口径混用」这类判定有据可依，而不是靠字符串匹配。

### 6.2 公司事实库（实例层）

索引 `(subject, period, metric)`，每条 Assertion 带 `source_spans`，支持：
- 点查：「启明信息 2023A 现金分红金额的已核验值」
- 反查：「这条公式在哪些案例上被验证过」（跨案件统计，为将来换 PG 留的口子）

### 6.3 注入纪律（你的第 2 条延续）

1. 领域知识只注入到 `t_compute` / `t_review` 与预测类结论的估计环节，不全程注入；
2. 预测类结论**只许给方法与口径，不许给结论数字**；
3. 库里的任何东西**不能覆盖规则代码的判定**。

### 6.4 数值规则的调整权（你的第 2 条，我部分改判）

你的直觉成立：精度写死在代码里迟早出事，项目上已经出过一次——
`PRECISION["元/10股"] = 2` 把「每 10 股派息 0.155」截成 `0.15`，复算少 90 万元，
错值还进了修改建议（`STATUS.md` 记的 TXX-009）。所以 v2.1 把数值规则从代码升为**知识**。

但「可调整」必须分两档，不能合成一档：

| 档 | 谁能改 | 生效范围 | 能不能进最终结论 |
|---|---|---|---|
| 草稿规则 draft | Agent 在调查中可当场新增或改精度并重算 | 只在本次 run 内 | **不能**。相关 Finding 只能到 `INSUFFICIENT` 或 `manual_review` |
| 权威规则 authoritative | 人审（第 8 节流程） | 全局，带 `version` 与 `previous_version` | 能 |

运行时的算术必须**带版本**：每次复算把 `rules_version` 与命中的 `rule_id` 写进 Finding，
于是「这条结论是按哪一版精度算出来的」事后可查、可重放。

**为什么不允许在跑的过程中静默改精度**：精度是复算的输入，改它等于改结果。
如果模型能在一次计算里把「元/10股」调回 2 位，`27,116,214.63` 那个错值就会重新变成「正确」。
所以灵活性的出口是「当场用草稿规则重算 + 明确标 tentative + 事后走人审」，
而不是「默默改一个全局变量」。

**另一半（你的第 4 条）：提取阶段禁止截断。** 数值从原文到断言不能丢信息：

| 阶段 | 做什么 | 禁止 |
|---|---|---|
| Span 提取 | 原样存 `raw_text` 与 `decimals_as_disclosed`（披露几位存几位，如 `0.155`） | 禁止在这里按 `PRECISION` 截断或四舍五入 |
| Assertion 构造 | 存原样字符串 + 全精度 `Decimal` | 禁止用「元/10股 = 2 位」这类显示规则处理原始值 |
| 计算 | 用全精度输入，按规则精度在**输出处**只舍入一次 | 禁止中间步骤反复舍入 |
| 显示 / 报告 | 按同一规则格式化 | 禁止与计算结果用不同精度（会造出文档里没有的数） |

每次舍入必须记 `rounding_step`（`calc_output` / `display`）、`rules_version`、命中 `rule_id`
与舍入前的全精度值。W 门为此新增一条 W6（见第 7 节）。

| 项 | 检查什么 |
|---|---|
| B1 概念绑定 | 指标名解析到标准概念（别名/简写命中知识库），不是字符串相似 |
| B2 事件状态与时态 | 已实施 / 已审议通过 / 预案 / 计划 / 预测，五者不得混用 |
| B3 统计范围 | 单一方案 / 本报告期合计 / 多年累计，三者不得混用 |
| B4 口径 | 合并 / 母公司 / 扣非 |

**权限不对称**：LLM 可以提出 `conflicted`（发现疑点就拦），但**不能批准 `bound`**——
批准权在规则与知识库手里。这是为了防止「语义理解正确」变成模型自己说了算。

### V（准备输出时，按需调 LLM）—— 这些证据能不能支撑这条结论

| 项 | 检查什么 |
|---|---|
| V1 逐条 Finding | 断言 / 判定 / 修正建议 / 引用页 |
| V2 引用存在且原文匹配 | **回查原 PDF**（`documents[].path`）；对不上则阻断该条 |
| V3 关系适用性 | Relation 的 `applicability` 是否成立（期间/口径/单位）；必要时**重跑 `t_compute`** |
| V4 Task State | 未处理的关键疑点、失败的工具调用、超授权操作、未完成的核查步骤 |
| V5 语义绑定状态 | 引用的 Assertion 必须 `attested + bound`；未绑定的只能出候选或 `manual_review` |
| V6 残余问题清单 | 报告必须附未解决主张与未解疑点清单，不许只报解决的部分（见 9.2 的 SR） |
| V7 发布决定 | 任一阻断 → `blocked` 或 `manual_review`，不得发布 |

### 两次校验为什么都要有

|  | 第 ④ 步 W | 最终核验门 V |
|---|---|---|
| 校验对象 | 单次工具返回结果 | 完整核查结论 |
| 核心问题 | 这份新数据能否安全登记 | 这些证据能否支持最终结论 |
| 执行频率 | 每次工具调用之后 | 准备输出结论时 |
| 失败处理 | 拒绝或标记异常数据 | 阻止无依据结论发布、降级或继续调查 |
| 是否调用 LLM | 默认不调用 | 复杂定性推理可选调用审查模型 |

一句话：**W 管「数据能不能进」，V 管「结论能不能出」。**
原文必须留档（Document 不删除、Span 不覆盖），不合格的候选抽取停在 `candidate`，
永远不能因为「后面要出报告」而被提升。

### 9.2 新增指标（agent 模式；RBA 挂起，实际计入 8 项）

| 指标 | 定义 | 分子 / 分母 | 数据来源 | 目标（先建口径，再谈达标） |

| 关系绑定准确率 RBA | Relation 的主体-谓词-客体与适用条件全部正确的比例 | 分子＝人工判定正确的 Relation 数；分母＝抽检 Relation 数（每案 ≥ 20 条） | `facts.sqlite` + 人工标注 | **挂起（你 2026-10-10 定）**：口径保留，暂不计入验收；需先建人工标注流程才测得出。挂起期间由 V3 在逐条层面兜住关系正确性，不做比例统计 |
| 无效工具调用率 ITR | **被拒**的调用占全部调用的比例（「零新增证据」不再算在内，见下） | 分子＝硬边界拒绝 + schema 非法 + 工具报错；分母＝总调用数 | `decisions.jsonl` | ≤ 0.15，且不得出现同类连续 3 次 |
| 无进展率 NPR | 执行成功但没推动调查的比例 | 分子＝既未改变任何主张状态、也未排除任何假设的调用；分母＝总调用数 | `decisions.jsonl` + `state.json` | 先建基线；偏高说明上下文没给够或动作集不匹配 |
| 主张解决率 SR | 本轮待核主张里被真正解决的比例 | 分子＝状态落到 `verified` / `insufficient`（带原因）/ `blocked`（带原因）的主张数；分母＝本轮全部待核主张数 | `findings.json` + `state.json` | 先建基线；**报告必须同时给出未解决清单** |
| 未来信息泄漏率 FILR | 决策上下文里出现 cutoff 之后线索的轮次占比 | 分子＝上下文含 `first_published_at > cutoff` 线索的轮次；分母＝总轮次 | `decisions.jsonl` | `historical_replay` 下 **0**（红线，见 4.4） |
| 推理证据支持率 CSR | 报告里数值与事实性陈述能找到出处的比例 | 分子＝有出处且通过 `explanation_guard` 的陈述数；分母＝全部此类陈述数 | 报告 + 证据库 | 1.0；违反即阻断该条（红线，不是打分项） |
| 时间截断违规率 CVR | 引用了晚于 cutoff 材料的比例 | 分子＝`pub_date > cutoff` 的引用条数；分母＝总引用条数 | 报告 + Document 表 | **0**；非零即整次运行作废（红线） |

**「进展」的定义**（决定 NPR 与 SR 怎么算）：主张状态变化（`open → evidenced / verified / blocked`）、
假设被排除（记进 `state.hypotheses`）、新增证据登记、以及**证据被否决**——最后一条也算进展，
因为排除一个错误假设本身就是有效调查。这就是你第 6 条那句话的落点：
「本轮没有新增证据」不等于无效调用。**被拒**（ITR）与**没推动**（NPR）是两件事，分开统计。

**可重放性验收（新增）**：同一 `run_id` 重放，`decisions.jsonl` 的动作序列、工具结果引用、
`rules_version`、材料快照 hash 必须逐项一致（只有时间戳可变）。做不到就不算可复现。
为此决策日志存**完整**内容而不是摘要：模型原文响应、工具原始结果、prompt 版本、
模型名与参数、代码版本（含自写工具 hash）、知识库版本、外部材料快照 hash 与 `retrieved_at`；
大对象（工具结果全文、网页正文）走内容寻址 `blobs/<sha256>`，日志里只留引用。

两个辅助指标（不进对外报告，只用于调参）：决策合法率（首次即合法的决策占比）、
单案成本（调用次数 / token / 时长）。RBA 仍挂起。

**两条纪律**：新指标在自造样本上只证明「口径能测」，不得当作泛化能力；
旧三项与新指标分开报，不许用固定模式的结果去证明 Agent 有效（你第 9 条的原话）。

## 12. 明确不做的事

1. **不搬 Hermes 的主循环**（`conversation_loop.py` 1781 行）：强耦合计费、供应商适配、
   上下文压缩、MoA、凭据，且为通用对话设计。要搬的是它的**判定逻辑**（打转守门、预算退还、
   质量门优先于模型判定这三条），不是它的循环。
2. **不搬 Hermes 的 SQLite 状态体系**：为多会话、网关、全文检索服务，对单机核查是超配。
3. **不引入图数据库 / 向量库作为知识库本体**（第 3 节）：先 SQLite，触发条件写死。
   向量检索如果将来要用，挂在 `t_recall` 下面做召回，不污染规则层的确定性。
4. **不做「模型改写知识库」**（第 8 节）。
5. **不把二手线索混进一手证据**（5.2）。
6. **不允许自写工具绕过三道门**：自写抽取器只能产出候选 Span，仍要过 W，仍受时间硬门与措辞守门人约束；沙箱内不得触网、不得读材料目录以外的文件、不得改动已有模块。
7. **不允许在运行中静默改数值规则**（6.4）：草稿规则可当场用，但结论只能标 tentative 并进人审。
8. **不执行未经 OS 级隔离的模型生成代码**（5.4，你第 5 条）：静态白名单不算沙箱；
   隔离没成型之前 `t_author_tool` 不启用，未知格式走声明式规格。
9. **不允许 cutoff 之后的线索进入决策上下文**（4.4）：即使它不作证据也不行——
   影响注意力就是泄漏。
10. **不允许在提取阶段截断数值**（6.4）：原样保存披露精度，舍入只发生在 `calc_output` 与 `display` 两个具名步骤。
